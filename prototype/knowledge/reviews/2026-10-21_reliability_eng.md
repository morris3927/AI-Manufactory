# 沖壓線模擬維修案例審核：設備保全工程師角色（2026-10-21）

> **聲明**：這是 AI 角色扮演的審核（模擬一位帶新進技術員看歷史工單的設備保全工程師），**不是真人專家審核**。案例本身全部是模擬資料。
> 審核範圍：`cases/stamping/` 120 筆（train 100、heldout 20）。修正的方法是改 generator 或加 post-process 規則，重新 build 後修正仍會保留。

## 2. 第一判斷錯誤（24 筆）逐筆結論

24 筆的第一判斷都抽自真正模式的 `distinguish_from`，在現場看來都是會犯的錯（誘導線索都有對應的 log 訊號）。有問題的是**推翻第一判斷的理由**和**數值的一致性**：

| 案例 | 問題 | 修正 |
|---|---|---|
| 0006 | 結果寫「角度正常」，但角度剛被從 215° 改成 200° | 改寫成實際觀察到的狀況 |
| 0014（heldout） | 換料後噸位上升 118→127 t，文字卻寫料「薄 8 條」 | 改為厚 0.08 mm |
| 0024 | 用「STRIP_EDGE 在 FD02 不在 PR01」當作排除理由，但邊緣偵測器本來就裝在送料機上 | 改用可觀察的區分：只觸發一次、換料在換模前而且當時生產正常；另由 generator 補上 log 缺少的換料事件 |
| 0030 | why 沒寫出真正誤導規則的線索 | 補上 15:09 送料誤差 0.06 mm |
| 0035（heldout） | 同一個料捲有兩次換料事件（01:08、02:17 spec_changed） | generator 合併成一次，文字時間同步修正 |
| 0049 | why 寫「首批就出現毛邊」，normalized 寫「逐漸變高」，兩者矛盾 | 統一說法 |
| 0061 | 證據寫「送料誤差 0.02 不符合跳屑」，但跳屑時送料本來就正常，這條推不翻跳屑 | 改用 log 裡真正的區分：02:07 提速前就已跳過 MISFEED |
| 0068 | log 的順序是先上浮、再降到 30、最後提速到 40，文字卻把「降速無效」寫成上鎖後才做的動作 | 照 log 時序重寫，用「提速前就已上浮」推翻跳屑 |
| 0073 | 寫 5.0 bar「低於下限」，但下限是 4.8 bar | 改為偏低、接近下限 |
| 0083 | ① 技術員自己檢查來令片，違反安全類只能停機通報的規定；② 寫同管路多台一起壓降，但 log 只有本機，而且根因是本機支管漏氣；③ 12.7° 被寫成「超限」 | 全文重寫；generator 修正 S3 判定（只有別台的氣壓訊號也下降時才升 S3） |
| 0088 | 平衡缸壓力高 0.4 bar，卻寫「每次增量」 | 改為調降到 3.9 bar |
| 0093 | 05:12 那次的處置被排在 06:03 的上鎖之後 | 依時間重排（`loto_at: 1`） |
| 0113 | 差值實際是 0.25 mm（文字寫 0.35）；121 t 比常態 142 t 低，文字卻寫「偏高」並拿來支持刃口磨耗 | 改正數值與推論 |

其餘 11 筆（0005、0015、0023、0042、0043、0054、0062、0078、0098、0103、0118）的推論都說得通，處置順序也合理：先停機上鎖，先做便宜的檢查，最後才換件。0098 只修了 generator 的重複換料事件。所有案例的停機時間和開單、結案時間都一致（validate 有檢查）。

## 3. 其他類型的主要發現

**誤報**
- 0045、0055、0064（heldout）：誤報劇情和觸發訊號接不起來，例如「首件誤用舊圖」不會觸發 DIE_PROTECT 或模具潤滑警報，攝影機反光也不會觸發 MES 的 MISFEED。全部重寫，generator 也加了 `FA_STORY_OVERRIDE`。0064 的 log 只有 1 次 MISFEED，文字卻寫「一直跳」，已改。
- 0094：先寫「斷電後手動檢查滾輪」，`loto_done` 卻是 false，這是沒上鎖就把手伸進夾捲點。已補 LOTO，並把劇情改成手動寸動穿料觸發 FD_POS_DEV。
- 0026、0036、0104：檢查定位銷、側導板、落料孔都要把手伸進去，但原本沒有上鎖，已補 LOTO。0114 改成只看已沖製品。
- 0074、0104：心得原本是「別看到超限就換煞車」「無堆料就直接重置」，容易被讀成可以輕忽，已改成先停機通報、上鎖確認。

**複合**
- 0090（不安全）：停止角 16.7° 超限，技術員自己檢查制動器，最後在仍然超限的狀態下列管並恢復生產。已改成停機通報，平衡缸調整後由設備工程師試機複測，回到上限內才試沖；制動器磨耗列為次因，由合格人員排修。
- 0080：原本用「調模高」遷就偏厚的料，改為隔離退料、換捲。
- 0016：多出一個不在根因裡的整平機原因，已刪除。0025、0051、0063：刪除和主因或次因矛盾的 log 讀值。0070：證據把距研磨的沖次誤當成模具累積沖次。0120：資料值是 3.9 bar，文字寫 4.0 bar。

**升級與 `new`**
- 0085：目錄外模式原本是「主馬達風扇故障」，解釋不了 AIR_LOW。改成平衡缸密封內漏造成機台耗氣異常，generator 加了 `NEW_MODE_OVERRIDE`。
- 0115：差值實際是 0.5 mm 且偏低，原文寫 0.3。偏低應該是壓印過深，原文寫成高度不足；移交理由也太弱，一併修正。
- 0018、0037：料捲問題的移交理由和內容改成退料換捲、需品保判定。

**典型**
- 數值或物理方向寫反：0013（噸位上升卻寫料偏薄）、0111、0112（heldout：模具資料卡應為 425.2，原文寫 424.4）、0096（設定表比例）。
- 用語錯誤：0082 寫送料機有「離合器」；0053 的「干油膠」。
- 0039：跳屑案例混進了彈簧疲勞的特徵。0081（heldout）：多台壓降和本機局部漏氣互相矛盾。
- 0110：光幕 MUTED 時有人進入危險區，屬於虛驚事件，原文沒有提報 near miss，已補上。

## 4. 為了重新 build 時保留修正而改的程式

- `_gen/case_skeleton.py`：
  - 新增 `merge_events`：誘導或次因帶進來的同一料捲、同一模具事件不再重複出現，規格變更的資訊會併到主事件。
  - 新增 `add_missing_change_signals`：recent_changes 有寫、log 卻沒有的換料或換模事件會補進 log。
  - S3 只在別台的氣壓訊號也下降時觸發。
  - 新增 `NEW_MODE_OVERRIDE`、`FA_STORY_OVERRIDE`。
  - 這些修改**都在亂數抽取之後才套用，不改變 RNG 序列**。我比對過：其他欄位，包括時間、技術員、停機時間、假設，全部沒有變動。
- `_gen/gen_cases.py`：
  - 套用 `case_patches.yaml`。替換字串沒有命中時，會在 CHECK 裡報 `patch not matched`。
  - 跨機台作業的上鎖步驟會寫出連動上鎖（LOTO-FEED-01 F6、LOTO-PRESS E5/E6）。
  - 上鎖後第一個寸動或空轉之前，插入 OSHA 1910.147(f)(1) 的測試／定位步驟。
  - 試沖之前插入恢復確認步驟（區分方式和 SOP 審核一致）。如果試沖只寫在 result 裡，會拆成獨立步驟。
  - 升級案例最後加上「保持上鎖、依 (f)(4) 換班移交」。
  - 審核簽核記在 `case_review.yaml`，綁定審核時草稿的 hash。草稿重新產生時，案例會自動退回 draft。新增 `approve` 子命令。
  - 改成就地覆寫檔案。原本是先刪除再寫入，會讓雲端同步產生 `CASE-STP-xxxx 2.json` 衝突副本（審核期間出現過兩次）。
- `_gen/validate.py`：
  - 檔名不合規的檔案（同步衝突副本）報 error，見 4.1。
  - `loto_done=false` 但步驟裡有動手作業（拆、定位銷、落料孔、更換…）時報 error。
  - `loto_done=true` 但沒有上鎖步驟時報 error。

### 4.1 macOS／雲端同步產生的重複檔（`CASE-STP-xxxx 2.json`）

- 審核開始時，`cases/stamping/` 和 `heldout/` 共有 120 個「` 2.json`」檔。其中 112 個和原檔逐位元組相同。另外 8 個（0027、0046、0056、0075、0085、0095、0105、0115，都是 new 或 escalated）不同，是在這些案例重新起草（23:00）**之前**的舊版本，內容例如 0027 寫「移交原廠技師」，但骨架寫的是模具技師。原檔名保留的是較新的版本，和 `_gen/raw/cases` 的快取一致。
- 第一次 assemble 後重複檔全部清除。之後又自動冒出 14 個，研判是 Desktop 雲端同步在「先刪除再寫入」時產生的衝突副本，內容都相同。改成就地覆寫之後，就沒有再出現過。
- `validate.py` 現在會把檔名不是 `CASE-STP-\d{4}.json` 的檔案報成 **error**，並且不讀入。測試過：複製出一個 `CASE-STP-0001 2.json` 會觸發 error，刪除後恢復正常。`assemble` 每次也會自動刪除這種副本。順手刪除了 `_gen/__pycache__/` 裡兩個「` 2.pyc`」。

## 5. heldout 檢查

- 品質和 train 相當。heldout 有 3 筆有修正（0014、0035、0112），另有 0064、0081 修了文字。
- 與 train 的 bigram Jaccard 最高值：raw 0.55（0021 對 0020），normalized 0.42。都低於 validate 的 0.6 門檻，沒有文字近似重複。
- **結構相似**：典型案例的訊號樣板是同一套，例如 0003 和 0001 是同一台機台、同一副模具、同一種訊號形狀。這是骨架設計造成的，評估時要知道 heldout 的典型案例對檢索來說偏簡單。

## 6. 剩下的疑慮

1. 這是 AI 角色扮演審核，approved 不等於業師簽核。Demo 前仍建議由真人抽查（至少錯誤判斷類 24 筆）。
2. heldout 的類型組成是：錯誤判斷 4、誤報 1、典型 15，**沒有 composite、escalated、new**。原因是 `assemble` 的分層抽樣遇到某模式沒有該類型時，會退回選典型案例。用來測 J5 的 `new` 分支不夠。要修就得重新抽 heldout，會改動既有的 split，所以這次沒有動，建議和 backend 協調後再調整。
3. 典型案例的 log 樣板高度一致，模擬器產生的 Demo 訊號也是同一套，評估分數可能偏高。
4. 部分數值是 LLM 自己編的，例如鎖緊扭力 8 N·m、25 N·m、側彎 4 mm/m，沒有標「模擬值」。案例屬於敘述，沒有列為錯誤，但仍建議統一標註。
5. 0007 的 normalized 有 324 字，超過 320 字的建議上限，只是 CHECK 警告，沒有修。
6. README 的「案例 review_status」欄仍寫 draft。README 不在我的範圍，沒有修改。
