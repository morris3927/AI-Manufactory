## 1. 部署形態

Demo 用**一台筆電跑全部**；訓練主機只負責訓練 YOLO。

```
┌──────────────────────── Demo 筆電 ────────────────────────┐
│                                                           │
│  frontend（Next.js，:3000）  ◄── REST / WebSocket ──┐      │
│                                                     │      │
│  backend「sentinel-core」（FastAPI，:8000，單一行程）│      │
│   ├ sim：攝影機模擬器、MES Log 模擬器、劇本          │      │
│   ├ vision：YOLO PPE、機台動態、關鍵幀擷取、人臉模糊 │      │
│   ├ bus：事件匯流（asyncio 佇列，topic 沿用 Kafka 設計）    │
│   ├ rules：規則引擎（CEP）、分級、分流、派工路由、升級       │
│   ├ jev：Jev client、事件判斷、看圖判斷、安全把關           │
│   ├ kb：Chroma 向量庫、檢索                                 │
│   ├ llm：DeepSeek client、診斷說明                          │
│   ├ agent：維修 Agent                                       │
│   ├ dispatch：工單狀態機、Discord 通知與按鈕                │
│   ├ audit：稽核紀錄                                         │
│   └ api：REST、WebSocket ──────────────────────────────────┘
│                                                           │
│  SQLite（sentinel.db）   Chroma（./chroma）   影片素材     │
└───────────────┬───────────────────────────────────────────┘
                │ HTTPS
   ┌────────────┼──────────────┬──────────────────┐
   ▼            ▼              ▼                  ▼
 OpenRouter   Ollama Cloud    Discord           （實驗室訓練主機
 Jev 1.14     DeepSeek V4.1   推播＋按鈕          只在訓練時使用）
```

**為什麼後端是單一行程**：Demo 只有一台機器；所有模組用 asyncio 在同一個行程裡跑，除錯最簡單。模組之間**只透過事件匯流和明確的服務介面溝通**，以後要拆成多個服務（Kafka＋微服務）時，介面不用改。

## 4. 事件匯流（bus）

### 4.1 Topic

| Topic | 誰發 | 誰收 | 內容 |
|---|---|---|---|
| `vision.events` | vision | rules、ws | 影像事件：PPE 違規、機台狀態、Jev 看圖結果 |
| `mes.logs` | sim.mes | rules、ws | 機台 Log：數值訊號、狀態、異常碼 |
| `access.events` | sim.roster | rules | 門禁進出 |
| `alerts` | rules | jev、dispatch、ws | 規則確認的異常（Incident） |
| `tasks` | dispatch | ws、notifier | 工單建立、狀態變更、指派、升級 |
| `ai.results` | jev、llm | dispatch、ws | Jev 判斷結果、LLM 說明 |
| `frames` | sim.camera | vision、ws | 影像幀（**只在程式內傳遞，不寫入資料庫**） |

### 4.2 事件共通格式

```python
class Event(BaseModel):
    event_id: str            # ULID，可依時間排序
    ts: datetime             # 事件發生時間（模擬時間）
    topic: str
    source: str              # "vision.ppe" / "vision.jev_feed" / "sim.mes" / "rules" ...
    line: str | None
    machine_id: str | None
    camera_id: str | None
    type: str                # 例如 "ppe_violation"、"feed_rate"、"machine_state"、"incident_opened"
    payload: dict            # 依 type 而定，見 schemas/
    trace_id: str | None     # 同一個異常從偵測到結案共用，稽核時串起整條鏈
```

### 4.3 實作

```python
class EventBus:
    async def publish(self, event: Event) -> None: ...
    def subscribe(self, topic: str, name: str, maxsize: int = 1000) -> asyncio.Queue[Event]: ...
```

- 每個訂閱者一個 `asyncio.Queue`；佇列滿時**丟棄最舊的 `frames`**（影像可以掉幀），其他 topic 不能丟，佇列滿要報警。
- 除了 `frames`，所有事件都同步寫進 SQLite 的 `event` 表，可以用來重播與稽核。

## 5. 模組設計

### 5.1 sim：輸入模擬（IN-1～4）

**攝影機模擬器**
```python
class VirtualCamera:
    camera_id: str
    async def play(self, video_path: str, loop: bool = False, fps: float = 15) -> None
    async def switch(self, video_path: str) -> None     # 劇本切換影片
    def latest_frame(self) -> np.ndarray | None          # 給前端串流與關鍵幀擷取
```
- OpenCV 讀 mp4，依 fps 等待後發布到 `frames`。
- 介面跟之後接 RTSP 的 `RtspCamera` 相同（同一個抽象類別 `CameraSource`）。
- 前端看畫面：`GET /api/cameras/{id}/stream`（MJPEG，畫上偵測框）。

**MES Log 模擬器**
- 每台機器每秒產生一筆：`spm`、`feed_rate`、`feed_length_error_mm`、`motor_temp_c`、`motor_current_a`、`tonnage_peak`、`state`（running／idle／alarm）、`alarm_code`。
- 正常值加上合理雜訊；劇本可以在指定時間注入變化（斜坡、歸零、跳變）。
- 訊號名稱與 `knowledge/failure_modes/*.yaml` 的 `log_signals` 一致。

**劇本（`data/simulated/scenarios/feed_jam.yaml`）**
```yaml
id: feed_jam
title: 場景 2：沖床送料卡料
cameras:
  CAM-STP-01: {video: assets/videos/stamping/feed_jam_01.mp4, then: assets/videos/stamping/normal_01.mp4}
mes_script:
  STP-L1-FD02:
    - {t: 0,  set: {feed_rate: 42, state: running}}
    - {t: 8,  ramp: {feed_length_error_mm: [0.02, 0.21], over_s: 6}}
    - {t: 14, set: {feed_rate: 0, alarm_code: MISFEED}}
expect:                                  # 端到端測試用
  incident: {type: feed_jam, severity: S2, within_s: 3}
  notify_within_s: 5
```
控制台按「場景 2」→ 載入劇本 → 同步啟動影片與 Log。

### 5.2 vision：感測（SE-1～6）

| 偵測器 | 輸入 | 頻率 | 輸出 `vision.events` |
|---|---|---|---|
| `ppe` | 整幀 | 每幀（15fps，可降到 5fps） | `ppe_violation {person_box, missing: [helmet], conf}`；同一人 3 秒內不重複發 |
| `motion` | ROI | 每幀 | `machine_state {state: running|idle, motion_score}`；狀態改變時才發 |
| `jev_feed` | ROI 關鍵幀 | 每 5 秒＋Log 異常時 | `jev_vision {p_jam, p_smoke, box}`（呼叫 `jev.vision`） |
| `face_blur` | 人員裁切圖 | 送出或儲存前 | —（工具函式） |

- PPE 判斷：偵測到 `Head`，且 Head 框與任何 `Helmet` 框的重疊比例 < 0.3 → 未戴安全帽。
- YOLO 在筆電上推論（Apple Silicon 用 `mps`）；權重從 `models/` 載入。
- `motion`：灰階 → ROI 幀差 → 指數移動平均；超過門檻判定運轉。門檻寫在 `plant.yaml`。

### 5.3 rules：規則引擎（RU-1～6）

**滑動視窗**：每台機器、每個訊號保留最近 10 分鐘的資料（`deque`），提供 `latest()`、`changed_within()`、`trend()`、`duration_true()`。

**規則寫法**
```python
@rule(id="R-STP-FEEDJAM", line="stamping", category="equipment", default_severity="S2")
def feed_jam(w: Windows, m: str) -> Finding | None:
    jam = w.vision(m, "jev_vision").latest()
    feed = w.mes(m, "feed_rate")
    if jam and jam.p_jam > 0.7 and w.vision(m, "jev_vision").count_above("p_jam", 0.7, last_s=15) >= 2 \
       and feed.latest() == 0 and feed.changed_within(30):
        return Finding(type="feed_jam", facts={
            "p_jam_last2": ..., "feed_rate_before": feed.max(last_s=60), "feed_rate_now": 0,
            "seconds_since_drop": feed.seconds_since_change()})
```
- 每條規則有固定 ID，命中時寫入稽核紀錄（GV-2）。
- `facts` 是**程式先算好的結論**，直接放進 Jev 的 state（Jev 不擅長算數）。

**Incident（異常事件）**
- 規則命中 → 找同一台機器、同類型、還沒結案的 Incident → 有就更新，沒有就開新的（RU-6 去重）。
- 新 Incident 發布 `alerts`，帶 `trace_id`。

**分流與派工路由**
```python
def route(incident) -> Plan:
    # 1) 事件類別 × 嚴重度（RU-3）
    #    safety: S2 → dispatch_only；S3 → emergency
    #    equipment: S2 → dispatch + ai；S3 → emergency + ai
    # 2) 指派對象（RU-4）：查當班 roster → 依職位挑人 → 門禁確認在廠 → 不在就改派
```

**逐級升級（RU-5）**：每張工單有升級計時器；在 `ack_timeout`（預設 S2 5 分、S3 2 分；Demo 可調成 30 秒）內沒有人接單，就升到下一個職位，並重新通知。

### 5.4 jev：直覺層（JV-1～5、SE-3/4、AG-4、CL-2）

```python
class JevClient:        # httpx.AsyncClient，連線保持不斷；啟動時先送一次暖機請求
    async def ask(self, state: dict, questions: dict, *, purpose: str, trace_id: str) -> JevResult
    # 每次呼叫寫入 jev_call 表：purpose、延遲、cost、model、輸入摘要、答案
    # 逾時 3 秒 → 拋出 JevUnavailable，呼叫端要有退路

judge.event(incident, similar_cases) -> EventJudgement      # J1–J3
vision.feed(frame, roi, machine) -> VisionJudgement          # V2
vision.ppe(person_crop_blurred) -> PpeJudgement              # V1
gate.step(step_text, machine_type) -> SafetyGate             # J4
gate.writeback(report, line) -> WritebackCheck               # J5
```
題目定義集中放在 `jev/questions.py`，**題目版本號**和結果一起記錄，事後分析時知道是用哪一版題目判斷的。

**事件判斷流程**
```
alerts（新 Incident）
 → kb.similar_cases(incident, k=5)
 → judge.event(...)
 → gate 決定：final_severity = max(規則判定, Jev 判定)；p_false_alarm > 0.9 且非 S3 → 標記疑似誤報，仍建單但不通知
 → 發布 ai.results {root_cause_top3, confidence, diagnosis_mode: jev_top3 | llm_deep}
```

### 5.5 kb：知識庫（KB-1、KB-2）

- Chroma 兩個 collection：`docs`（SOP、法規、指引、故障模式）、`cases`（維修案例）。

### 5.7 agent：維修 Agent（AG-1～6）

**一張工單一個 Agent session**，對話紀錄存在 `agent_message` 表。

**工具（Agent 可以呼叫）**

| 工具 | 作用 |
|---|---|
| `get_workorder()` | 工單、Incident、Jev 根因前三名 |
| `get_machine_signals(signal, last_min)` | 查詢 Log 視窗（已算好的摘要，不是原始資料） |
| `get_sop(failure_mode_id, phase)` | 取 SOP 的某一段 |
| `search_cases(query)` | 找相似案例（包含第一判斷錯誤的案例） |
| `record_step(step, result)` | 記錄技術員回報的步驟結果 |
| `request_supervisor(reason)` | 要求主管確認 |

**程式強制的規則（不靠提示詞）**
1. **作業許可先行**：`PERMIT_APPROVED` 之前，Agent 只能顯示作業許可與 LOTO 的預覽。
2. **LOTO 先行**：`LOTO_DONE` 之前，Agent 的回覆**只能是 LOTO 清單與準備步驟**。程式不會把 `get_sop(phase=inspect|repair)` 開放給 Agent；排查與維修段落只在 `IN_REPAIR` 開放。
3. **安全把關**：Agent 每次回覆前，程式把回覆裡的步驟送給 `jev.gate.step`；任一機率 > 0.3 → 在前端把該步驟標紅，並自動呼叫 `request_supervisor`。
4. **不能叫人復電**：輸出檢查器過濾「可以復電」「解除上鎖」這類指示，改成「請由原上鎖人依 LOTO 解除程序執行」。
5. Agent **不能改變工單狀態**；狀態只能由人在介面上操作。

🔬 DeepSeek 經 Ollama 的 tool calling 是否穩定要實測；不穩就改成「程式先決定要查什麼、Agent 只負責寫回覆」的固定流程。

### 5.8 dispatch：工單與通知（WO-1、NT-1～3）

**工單狀態機**

```
OPEN ──指派──► ASSIGNED ──接單──► ACKED ──申請許可──► PERMIT_REQUESTED ──班長核准──► PERMIT_APPROVED ──LOTO 勾完──► LOTO_DONE ──► IN_REPAIR
  │               │ 逾時未接                                                    │
  │               └──► ESCALATED（重新指派上一級，回到 ASSIGNED）                ▼
  │                                                              PENDING_VERIFY（Checklist 勾完）
  └──主管標記誤報──► CANCELLED                                                   │ 回報通過 J5
                                                                                 ▼
                                                                               CLOSED
```
- 安全類工單（PPE）流程較短：`OPEN → ASSIGNED → ACKED → CLOSED`，不需要 LOTO。
- 每次轉換寫入 `workorder_transition`（誰、何時、從哪個狀態到哪個狀態、原因）。

**Discord**
- 一條產線一個頻道，加上 `#緊急` 頻道（S3）。
- 通知用 embed：嚴重度顏色、機台、根因前三名（含機率）、SOP 編號、工單連結；附按鈕「接單」「轉派」。
- LLM 說明完成後，以同一則訊息的回覆補上。
- 用 `discord.py` bot；按鈕事件呼叫 dispatch 服務。Discord 帳號 ID 和人員對應寫在 `roster.csv`。
- 評審可以掃 QR code 加入 Demo 伺服器的「觀眾」頻道，看到同樣的通知（只能看，不能按）。

### 5.9 audit：稽核（GV-2）

`audit_log` 一律只新增、不修改：`ts`、`trace_id`、`actor`（system／jev／llm／人員 ID）、`action`、`detail`（JSON）。前端「稽核時間線」依 `trace_id` 把同一件事從偵測到結案串起來。

## 8. 前端

### 8.1 技術

Next.js（App Router）＋ TypeScript ＋ Tailwind ＋ shadcn/ui ＋ 圖表庫（Recharts）。深色「戰情模式」，**最小寬度支援手機**（技術員畫面）。

### 8.2 畫面

| 路徑 | 畫面 | 主要元件 | 對應功能 |
|---|---|---|---|
| `/` | **戰情儀表板** | 攝影機牆（2×2，可放大，疊偵測框與 Jev Box）；產線卡片（機台健康燈號、稼動率）；即時告警串；嚴重度分佈；「規則 vs AI 處理比例」小圖 | UI-1 |
| `/kanban` | **任務看板** | 欄位：待處理、處理中、待確認、已解除；卡片：嚴重度色條、機台、負責人與職位、計時器、升級次數；可篩選產線 | UI-2 |
| `/workorders/[id]` | **任務詳情** | 左：事件資訊（關鍵幀＋Box、訊號圖、時間線）；中：**根因前三名機率長條圖**、LLM 說明、SOP；右：**作業許可 → LOTO 清單 → 維修 Agent 對話**（依狀態解鎖）、Checklist、結案回報；下：稽核時間線 | UI-3 |
| `/m/[workorderId]` | **技術員手機版** | 只有：工單摘要、LOTO 勾選、Agent 對話、Checklist、回報 | UI-6 |
| `/control` | **控制台** | 劇本按鈕；每支攝影機的影片選單；重置 Demo；升級逾時秒數；Jev 開關（展示退路） | UI-4 |
| `/metrics` | **效益頁** | 反應時間（發現、通知、到場）、MTTR、AI 成本累計（真實 `usage.cost`）、校準曲線、規則／Jev／LLM 比較表 | UI-5 |
| `/audit` | **稽核查詢** | 依 trace_id 或工單查詢完整時間線 | GV-2 |

### 8.3 角色切換

Demo 不做登入，右上角下拉選單切換身分：技術員、班長、主管、評審（唯讀）。後端依身分檢查權限（GV-6），例如只有班長能核准作業許可、只有主管能覆寫。

## 9. 關鍵流程時序（場景 2：沖床卡料）

```
t=0     控制台按「場景 2」→ 攝影機模擬器播放卡料影片；MES 模擬器開始送 Log
t=8s    feed_length_error_mm 開始上升（Log）
t=10s   jev_feed 定時關鍵幀 → Jev V2：p_jam=0.82，Box 框出板材        [約 0.6–1.5 秒 🔬]
t=14s   feed_rate=0、alarm MISFEED → Log 異常觸發加送關鍵幀 → Jev V2：p_jam=0.88
t=14.1  規則 R-STP-FEEDJAM 命中（連續 2 張 >0.7 ＋ 送料速率歸零）→ Incident（S2，設備類）
t=14.2  kb.similar_cases → Jev J1–J3 → 根因前三名＋機率                [約 0.5 秒]
t=14.8  dispatch：查班表 → 指派當班技術員 → 建工單 → Discord 推播（含根因機率）
        ── 事件發生到通知送出 < 1 秒（從規則命中算起）──
t=15    LLM 說明開始產生 → 約 1.5 秒後以回覆補上
t=…     技術員在 Discord 按「接單」→ ACKED → 手機頁出現 LOTO 清單
        申請作業許可 → 班長核准 → 勾完 LOTO → LOTO_DONE → Agent 開始引導排查
        （2026-10-21 調整：作業許可在 LOTO 之前，對齊一般作業許可實務）
        Agent 建議「伸手取出卡料」→ J4 判定 enters_danger_zone=0.9 → 標紅、要求主管確認
        第一個根因無效 → Agent 依下一個根因給步驟 → 修好
        Checklist 勾完 → 提交回報 → J5 檢查完整 → 寫回知識庫（draft）→ CLOSED
```

## 11. 容錯

| 失敗 | 系統行為 |
|---|---|
| Jev 逾時或錯誤 | 規則照常建單派工；通知註明「AI 判斷暫不可用」；看圖規則改用「Log 送料速率歸零＋動態分數歸零」 |
| LLM 逾時 | 派工通知已送出不受影響；說明欄顯示「說明產生中斷」；Agent 改顯示 SOP 原文 |
| Discord 斷線 | 工單照建；前端 Kanban 仍即時更新；恢復後補送 |
| 影片讀取失敗 | 攝影機畫面顯示「訊號中斷」→ 發布 `camera_offline` 事件（這本身就是一種異常） |

## 12. 測試

| 層級 | 內容 |
|---|---|
| 單元測試 | 規則（給定視窗資料 → 是否命中）、路由、狀態機、Jev 回傳解析、LOTO 先行的限制 |
| 劇本重播（端到端） | 用假的 Jev／LLM 回應（固定值）跑每個劇本，檢查 `expect` 是否達成；**每次提交都要跑** |
| 真實 API 測試 | 標記 `@pytest.mark.live`，需要金鑰，手動執行 |
| 評估 | `eval/`：測試集、校準曲線、延遲統計 → 產出成果說明書的圖表 |
