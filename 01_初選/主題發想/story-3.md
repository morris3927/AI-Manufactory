# AI Manufacturing 2026 競賽提案：主題一系統規格企劃書（v3 整合版）

> 版本說明：v3 在 v1（完整閉環）、v2（創新點）基礎上，修正「全部包成 LLM」的問題，
> 改為 **「確定性事件交給規則、需要判斷的環節才請 Agent 出場」** 的分層架構。
> 兩個 AI 介入點是刻意設計的：① 偵測後的「診斷推論(LLM+RAG)」、② 派工後的「任務型維修 Agent」。

---

## 一、 競賽主題與核心主張

* **參賽主題：** 主題一「AI × 智慧現場：全知辨識與即時響應」
* **核心主張（一句話）：** 打造「偵測 → 診斷 → 派工 → 現場協作 → 回報 → 知識回寫」的自動化閉環；
  其中**確定性的偵測與告警交給規則(快、可稽核)，需要推理判斷的診斷與檢修協作才交給 AI Agent(準、會學)**。
* **設計理念（也是本案最大差異化）：決策權的分層分配**
  * 我們**不把所有判斷丟給 LLM**——那樣慢、貴、且安全告警不可稽核。
  * 規則引擎處理「確定性、要秒級反應、要可解釋」的事件(95%)。
  * AI Agent 只在「規則覆蓋不到、需要像人一樣推理」的兩個環節介入(5%)。
* **應用場域(本案鎖定)：伺服器機殼製造廠**
  * 以主辦贊助商 **勤誠興業(Chenbro,全球前三大伺服器機殼廠、NVIDIA 供應鏈)** 所屬之伺服器機殼製造為應用情境。
  * 製程:鈑金沖壓 → 折彎 → 銲接 → 表面處理 → **人工組裝**(機殼 / 電源 / 線材 / 背板整合)→ 測試。
  * 選此場域之理由:(1) 機台稼動率與工安是該產業核心 KPI,與本系統高度契合;(2) 勤誠正擴建馬來西亞、美國新廠,「**新廠快速上線 + 老師傅經驗跨廠傳承**」正是本案維修 Agent 與知識回寫的價值所在;(3) 直接呼應競賽「產業特別獎」。
  * 合規:依簡章使用公開資料集與模擬資料,僅以該產業為情境,不涉及企業機密。

## 二、 系統分層架構：快路 (確定性) × 慢路 (Agent)

```
┌── 感測層 (Sensing) ──────────────────────────────────────────┐
│  影像串流 ─► CV 模型 (YOLO 等) ─► 影像事件                    │
│  MES Log  ─► 門檻 / 規則判定   ─► 設備事件                    │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌── 快路 Fast Path (規則引擎 / CEP，零 LLM 成本) ──────────────┐
│  • 嚴重度分級 L1 / L2 / L3                                     │
│  • 已知跨模態組合即時告警(安全優先，毫秒級)                 │
│  • 依員工職掌(Role)路由出正確的派工對象                     │
└───────────────────────────┬──────────────────────────────────┘
              (L2 / L3 異常才往下啟動 AI；L1 僅記錄)
                            ▼
┌── AI 介入點 ① 診斷推論 (LLM + RAG / CBR) ────────────────────┐
│  輸入：本次事件 + 機台上下文 + 近 N 分鐘事件時間線            │
│  檢索：SOP 知識庫 + 歷史維修案例庫                            │
│  輸出：top-k 可能根因 + 對應處置建議(附信賴排序)            │
│  → 把「可能問題與解法 + SOP」打包進派工通知                  │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌── 派工 Dispatch ─────────────────────────────────────────────┐
│  Slack / Discord / Email 通知 → 現場檢修人員                  │
│  主管收總體進度通知；工程師收具體工單 + 診斷建議             │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌── AI 介入點 ② 任務型維修 Agent (Task-bound Repair Agent) ────┐
│  綁定：本張工單 + 該機台上下文 + RAG 知識庫                  │
│  • 檢修人員可即時問答(針對這顆機台、這個故障)             │
│  • 引導逐步檢修邏輯;前述方法無效 → 動態給進階/長尾排查      │
│  • 全程收集人員回報的「真實故障原因與有效解法」             │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌── 結案與閉環 (一般程式邏輯) ─────────────────────────────────┐
│  • Checklist 逐項勾選 → 「確認解除」事件才正式關閉           │
│  • Agent 把人員回報消化成結構化知識 → 寫回 RAG(自我進化)   │
│  • 戰情儀表板即時更新任務狀態與機台健康度                    │
└──────────────────────────────────────────────────────────────┘
```

## 三、 各層職責與技術選型(以及「為什麼是這個方法」）

### 1. 感測層 — 確定性,不用 LLM

* **影像事件(YOLO 類，純視覺 / 視覺 + 幀間移動量）：**
  * 工安 / 現場：未戴安全帽或護具(PPE)、闖入危險區、人員跌倒。
  * **機台運作狀態：運轉 vs 閒置(Idle)** — 以 YOLO 定位機構 + 幀間移動量,判斷主軸 / 輸送帶 / 機械手是否在動。
  * 物料異常：堵料、卡料、缺料(以區域判定)。
  * (可選)機台外觀異常：冒煙、火花。
* **設備事件(對 MES Log 做門檻 / 規則判定）：** 機台閒置(Idle)、馬達高溫、系統回報異常碼。
* **為什麼不用 LLM：** 看影像 / 讀數值是 CV 與規則的本行,快、便宜、穩定。
* **核心設計：** 影像判斷的「運轉 / 閒置」會與 MES Log 的運作狀態**交叉比對**(見快路)——這是本案最具代表性的跨模態驗證點。
* **產線專屬的視覺辨識(重要設計)：不訓練「一個什麼都能判斷的大模型」,而是依不同產線 / 工段部署各自針對性的輕量辨識模型與事件清單。**
  * 例(對應勤誠製程)：
    * **沖壓段** → 沖床運轉 / 閒置、送料卡料 / 堵料。
    * **銲接段** → 火花 / 煙霧、銲接機器人運轉狀態。
    * **組裝段** → 人員在崗、PPE、工序合規。
  * **好處：** 模型小而準、邊緣端算力低、易維護;辨識內容貼合該工段真實需求,避免一個通用大模型樣樣會、樣樣不精。
  * **擴充機制(新異常事件導入)：** 新增一條產線 = 套用一份「**辨識設定檔(Detection Profile)**」+ 增訓該線專屬事件,而非牽動全系統;每條產線維護自己的事件清單與訓練資料,部署流程標準化。

### 2. 快路 Fast Path — 規則引擎 / CEP，95% 事件在這裡解決
* **嚴重度三級分級：** L1 Normal(僅記錄)／L2 Warning(需處理、無立即停機危險)／L3 Error(重大、需立刻排除)。
* **已知跨模態組合告警：** 以 CEP 規則處理可預先定義的高風險組合。
  * 例 1(核心)：影像判斷「機台 Idle / 無動作」 vs MES Log「顯示運轉中」→ 兩者不一致 → 感測器或 Log 失準 → 告警。
  * 例 2：影像 Idle + Log Idle 且持續 N 分鐘 → 確認真閒置 → 派工查原因。
  * 例 3：Log 馬達高溫 + 影像現場無人 → 升級 L3 緊急通報。
  * **我們誠實地把它寫成規則,而不是包裝成 AI**——安全告警必須毫秒級、可稽核、可解釋。
* **依職掌路由：** 查表決定派工對象。
* **為什麼不用 LLM：** 這些是確定性決策,且安全相關事件不能等 LLM、不能交給黑箱。

### 3. AI 介入點 ① 診斷推論 — LLM + RAG / 案例式推理(CBR)
* **觸發時機：** 僅 L2 / L3 異常觸發(不是每幀每筆 Log 都呼叫 → 成本可控)。
* **運作：** LLM 讀取「本次事件 + 機台上下文 + 近 N 分鐘事件時間線」,從 SOP 庫與歷史案例庫檢索,
  輸出 **top-k 可能根因 + 對應處置建議**(例：80% 感測器髒污→先擦拭；15% 皮帶鬆脫…)。
* **誠實版說明：** 機率排序來自**歷史案例檢索 + LLM 排序(CBR)**,不宣稱訓練了一個獨立機率模型;
  模擬/公開資料下即可實現,Demo 效果相同。
* **價值：** 現場人員拿到工單時，已附「可能問題與解法」,不必盲目排查。

### 4. AI 介入點 ② 任務型維修 Agent — 真正的 Agent 在這裡
* **這是全系統唯一「有狀態、會對話、會用工具」的 Agent，綁定單一工單與機台。**
* **功能：**
  1. **現場問答：** 檢修人員可直接問「這顆機台這個故障要先檢查什麼」,Agent 以該機台上下文 + RAG 回答。
  2. **引導檢修邏輯：** 帶著人員逐步排查；若診斷建議的前幾項無效,動態給出進階/長尾(罕見)排查指令。
  3. **回收檢修邏輯：** 全程記錄人員實際操作與回報,作為知識回寫的素材。
* **為什麼這裡才需要 Agent：** 開放式、動態、需要逐輪推理與機台情境記憶——正是 LLM Agent 的強項，
  也是規則做不到的「需要人為判斷」之處。

### 5. 結案與閉環 — 一般程式邏輯 + 一次 LLM 摘要
* **Checklist 確認解除：** 狀態機，確保每個異常都被追蹤關閉(不需 AI)。
* **知識自我進化：** 結案時 Agent 用 LLM 把人員的自由文字回報**消化成結構化知識,append 寫回 RAG**。
  * 誠實版:只做「知識增量寫回」(真的能 Demo)，不宣稱模型自動再訓練。
  * 價值：工廠運作越久，案例庫越完整，新進工程師也能擁有老師傅級判斷力。

## 四、 目標架構 vs 本次實作範圍(化解「野心 vs 可行性」）

> 此區塊刻意分兩層寫，同時對應評分的「創新性(看得遠)」與「可行性(做得出)」。

| 元件 | 目標架構 (Production) | 本次原型實作 (Demo) |
|---|---|---|
| 影像來源 | 邊緣端輕量模型過濾、僅推關鍵幀(省頻寬、可擴充) | 直接用公開資料集 / 錄製影片跑 CV |
| 訊息佇列 | Kafka 高吞吐 | 輕量 queue / async pipeline(Demo 效果相同) |
| 快路規則 | 完整 CEP 引擎 | 規則集 + 三級分級 |
| 診斷推論 | LLM + 完整案例庫 | LLM + 自建 SOP/案例庫(RAG) |
| 維修 Agent | 多機台、多工單併行 | 單一場景、單工單對話 Demo |
| 資料來源 | 真實 MES / 攝影機 | 公開 PPE/工安資料集 + Log simulator(依簡章允許) |

* **邊緣運算、Kafka 寫進「目標架構」展示遠見，但不在原型主推、不做為 Demo 重點**——避免被質疑是來做基礎建設而非 AI。

## 五、 資料策略(可行性的證據，文件必寫)

1. **影像：** 公開 PPE / 工安資料集(安全帽、護具、危險區、跌倒)→ 真實可訓練。
2. **設備 Log：** 自寫 simulator 依機率產生 Idle/高溫/異常碼,**時間戳與影像事件對齊**,以製造跨模態場景。
3. **SOP / 案例庫：** 自建「故障模式 ↔ 根因 ↔ 處置」表，作為 RAG / CBR 來源。
4. **產線專屬辨識設定檔：** 依伺服器機殼製程,分沖壓 / 銲接 / 組裝三段,各自維護事件清單與訓練資料(對應上節「產線專屬視覺辨識」)。
5. 明示「依簡章規定使用公開資料集與模擬資料，不涉及企業機密」。

## 六、 預期效益(量化模型，價值性 30% 的命脈)

### 6.1 產業基準(數字依據,避免空談)

| 指標 | 公開產業基準 | 與本系統的關聯 |
|---|---|---|
| 離散製造 OEE | 中位數約 **60%**、前段班約 75%、世界級 **85%** | 我們以提升可用率推升 OEE |
| 非計畫停機 | 即時 / 預測式維護首年可降 **30–50%** | 自動偵測 + 引導維修縮短停機 |
| MTTR(平均修復時間) | 導入後降 **20–40%**(搭配故障歷史可達 40–60%) | 診斷建議 + 維修 Agent 消除無效排查 |

> 註：本系統屬「即時偵測 + 引導維修」,機制對應上表「降非計畫停機」「降 MTTR」兩條,故引以為合理性背書。
> 刻意不引用「每小時停機損失 $260K」一類數字——該數據源自汽車大廠,套用於機殼產線將過度誇大。

### 6.2 假設情境試算(以一條沖壓 / 銲接產線為例)

> 以下為**假設情境之模擬推估**(取值保守、落在上表區間內);初選以模型呈現,決賽以 Demo 測試數據替換。

* **基準設定：** 計畫生產時間 16h × 22 天 = 352 h/月;每月停機 60 次,每次 = 發現延遲 12 分(人工巡檢)+ 修復 30 分 = 42 分 → 月停機約 **42 h(≈12%)**。

| 指標 | 現況(人工巡檢) | 導入後 | 改善 |
|---|---|---|---|
| 異常平均發現時間 | 約 12 分鐘 | 約 0.5 分鐘(秒級) | ↓ **>95%** |
| 平均修復時間 MTTR | 30 分鐘 | 22.5 分鐘 | ↓ **25%**(保守,基準 20–40%) |
| 每月非計畫停機 | 約 42 h | 約 23 h | ↓ **45%**(基準 30–50%) |
| 設備稼動率 OEE | 約 60% | 約 64% | ↑ **約 4 個百分點** |
| 每月回收產能 | — | **約 19 h / 線** | 直接轉為產出 |
| 每事件 AI 成本 | — | 僅 L2/L3 觸發 LLM(約 60 次/月) | 可控、可估算 |

* **成本論點(差異化)：** LLM 只在約 5% 的異常事件觸發，非每幀呼叫 → 每月僅數十次推論,token 成本極低,這是真實營運論點。
* **永續/治理面：** 安全告警走可稽核的規則路徑(非黑箱)；維修知識永久留存、隱性知識資產化——尤其支援勤誠**馬來西亞 / 美國新廠快速上線與跨廠經驗傳承**。

## 九、 技術實作深化(決賽用主檔;初選擇要納入)

### 9.1 模型訓練(產線專屬)
* **方法:** 以預訓練 YOLO 為基礎做**遷移學習**,各工段分別微調,不從零訓練。
* **資料來源:** 公開資料集(PPE / 工安 / 表面瑕疵)＋ 現場錄影標註 ＋ 資料增強 / 合成(模擬卡料、煙霧、低光)。
* **訓練流程:** 蒐集 → 標註 → 微調 → 驗證(mAP / Precision / Recall)→ 部署 → 監控資料漂移 → 迭代。
* **產物:** 每工段一份 **Detection Profile**(類別清單 + 權重檔 + 對應觸發規則)。
* **新事件導入:** 小樣本標註 + 增量訓練,只更新該產線的 Profile,不動其他產線。

### 9.2 LLM 選型:線上 vs 地端(資安關鍵決策)
| 方案 | 優點 | 缺點 |
|---|---|---|
| 線上雲端 API(如 Claude / GPT 類) | 推理最強、零維運、隨時更新 | **資料外送 → 工廠機密疑慮** |
| 地端開源模型(如 Llama / Qwen 類,自架 GPU) | **資料不出廠、可控、可離線** | 需 GPU 算力、推理略弱 |
* **本案建議:混合分層,預設走地端。**
  * 含廠內資料的診斷與維修對話 → **地端開源模型**(資料主權)。
  * 僅地端信心不足的長尾複雜案例,**經去識別化後**選擇性升級雲端。
  * 呼應簡章資安要求,且對勤誠(服務 NVIDIA / Google、NDA 嚴格)最具說服力。

### 9.3 Kafka 資料管道
* **Producers:** 邊緣 CV 節點(影像事件)、MES Log Adapter、門禁系統 Adapter。
* **Topics(範例):** `vision.events` / `mes.logs` / `access.events` / `alerts` / `tasks`。
* **Consumers:** CEP 規則引擎、診斷服務、戰情儀表板、資料封存。
* **時間同步:** 各事件皆帶時間戳,中控以時間窗對齊,作為跨模態關聯的依據。
* **原型作法:** 用輕量 queue 或單機 Kafka,Topic 與 schema 設計不變、等比例縮小。

### 9.4 前端畫面與系統樣式
* **戰情儀表板:** 即時機台健康度、稼動率、當前告警分佈。
* **任務看板(Kanban):** 待處理 / 處理中 / 已解除三欄;卡片含嚴重度、負責人、計時。
* **任務詳情頁:** 診斷建議(top-k 根因)、SOP、Checklist、**維修 Agent 對話視窗**。
* **報表頁:** MTTR、停機、OEE 趨勢與效益量化。
* **技術 / 樣式:** React / Next.js + WebSocket(即時推播)+ 圖表庫;工業深色「戰情模式」介面。

### 9.5 介面串接(整合架構)
* **後端 API:** REST(查詢 / CRUD)＋ WebSocket(即時事件推播)。
* **模組解耦:** CV 服務、CEP、診斷(LLM)、維修 Agent、通知、門禁 / MES Adapter 全以事件匯流(Kafka)解耦。
* **通知整合:** Webhook 串接 Slack / Discord / Email。
* **權限:** 角色化存取控制(主管 / 工程師 / 訪客)。

### 9.6 機台負責人與門禁整合 ── 責任追溯與精準派工(新增亮點)
* **資料串接:** 介接產線門禁 / 刷卡資料,建立「**時段 × 區域(機台) × 負責工程師**」對應關係。
* **應用一:精準派工** — 異常發生時,依當下班別與負責人,**直接指派該機台當值負責人**,而非全體廣播,縮短到場時間。
* **應用二:責任追溯與持續改善** — 記錄異常時段之負責人與處理歷程,形成可追溯紀錄,供**績效分析與流程改善(正向、非懲罰導向)**。
* **個資與治理(務必寫明):** 依簡章資安與個資要求,人員資料採**角色化 / 去識別化**處理、存取受權限控管;對外定位為「**責任歸屬與可追溯性**」,避免「咎責 / 懲罰」框架引發勞資與個資爭議。
